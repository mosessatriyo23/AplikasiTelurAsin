# Runbook operasi (operator, Indonesia)

## Persiapan dan rilis

- Simpan konfigurasi di secret manager / `.env` lokal (jangan commit). Jalankan `npx tsx scripts/validate-environment.ts` setelah variabel terisi; pemeriksaan hanya mencetak nama field, bukan isinya. `APP_URL`/`NEXT_PUBLIC_APP_URL` harus origin publik yang benar, HTTPS di production. Perubahan `NEXT_PUBLIC_*` memerlukan build ulang. Sandbox Midtrans dahulu; konfigurasi notification URL publik `/api/midtrans/notification` dan cek delivery. Jalur pembayaran saat ini **redirect/popup hosted**, bukan jaminan dukungan semua metode Snap dalam iframe browser. Uji redirect, callback, tile peta, push, CSP pada browser target sebelum live.
- Bekukan seluruh writer (server, webhook, cron, workers, skrip administrasi), catat versi aplikasi/schema dan waktu. Ambil backup konsisten **database lengkap** dengan tool mesin DB sesuai `DATABASE_URL`, terenkripsi, akses terbatas; jangan simpan backup/manifest berisi PII di repo. Uji restore backup ke DB terisolasi dan verifikasi jumlah order/item, produk, batch, admin, serta sampel status pembayaran tanpa menampilkan PII di log. Snapshot JSON dari skrip stok **bukan** backup DB.
- Jalankan migrasi schema yang disetujui untuk versi rilis (jangan gunakan `db:push` sebagai strategi migrasi produksi), `npx prisma generate`, lalu tes dan build. Untuk rollback kode, hentikan writer; skema yang telah dimigrasi mungkin tidak kompatibel dengan kode lama. Jika perlu rollback data, putuskan webhook/payment dahulu, rekonsiliasi transaksi Midtrans eksternal yang terjadi setelah backup, restore backup yang telah diuji dan verifikasi ulang sebelum membuka akses. Jangan menimpa pembayaran terkonfirmasi hanya karena backup lebih lama.

## Rekonsiliasi tanggal dan stok historis

- `scripts/migrate-two-day-stock.ts` sengaja dinonaktifkan: tanggal kedatangan historis tidak bisa dipastikan dari `availableAt`. Jangan otomatis menggeser tanggal lama. Untuk stok: inventaris fisik, cek reservasi yang sudah dikurangi, susun manifest `products` dengan `{id, expectedStock, ready, pending:[{quantity,readyDate:"YYYY-MM-DD"}]}` mencakup semua produk; jumlah ready+pending harus sama dengan **stok net** existing (jangan kurangi pesanan dua kali). Gunakan `npx tsx scripts/reconcile-ready-stock.ts <private-manifest.json>` untuk dry-run, audit snapshot lokal. Setelah DB backup diuji dan semua writer berhenti, `npx tsx scripts/reconcile-ready-stock.ts <private-manifest.json> --apply --backup-verified`. Jangan jalankan berulang atau pada batch yang sudah ada. CAS dan transaksi akan batal jika stok berubah.
- Untuk `OrderItem.readyAt` NULL: jangan mengambil tanggal batch saat ini atau tanggal order secara spekulatif. Investigasi bukti setiap item, buat manifest terpisah `{ "items": [{ "id": "...", "productId": "...", "orderCreatedAt": "ISO dari DB", "readyDate": "YYYY-MM-DD" }] }` untuk **semua** item belum diketahui. Bila bukti tak tersedia, biarkan NULL dan eskalasi manual; jangan buat tanggal palsu. Dry-run `npx tsx scripts/backfill-order-item-readiness.ts <private-manifest.json>` menulis snapshot lokal pribadi; lakukan full DB backup terverifikasi dan hentikan writer sebelum `--apply`. Transaksi serializable + CAS membatalkan perubahan bila item/createdAt bergeser. Jadwalkan audit item yang masih NULL setelah rilis. Hapus snapshot/manifest dengan prosedur retensi PII.

## Rate limit, worker, dan deployment

- SQLite hanya didukung pada **satu file persisten bersama**, bukan filesystem ephemeral dan bukan salinan SQLite berbeda pada tiap instance. Counter rate limit persisten berada pada tabel `RateLimit`; beberapa proses pada host yang sama harus menunjuk file yang sama. Untuk replika lintas host dibutuhkan datastore bersama yang benar sebelum deployment tersebut didukung.
- Default tidak mempercayai forwarded IP dan menggunakan bucket bersama (konservatif, dapat membatasi pembeli lain). Atur `TRUSTED_CLIENT_IP_HEADER` hanya bila ingress terpercaya menghapus header inbound dan menuliskan tepat satu IP, serta origin server tidak dapat diakses langsung. `x-forwarded-for` dan `forwarded` sengaja ditolak. Jangan mengaktifkannya hanya karena header tersedia.
- Login dibatasi per IP dan username dengan backoff progresif; order 8/jam/identity, checkout 15/15 menit, refresh publik 20/15 menit. Review angka setelah observasi trafik. Rate limit tidak sama dengan verifikasi identitas pembeli; serangan terdistribusi masih perlu kontrol edge dan monitoring.
- Setelah migrasi disetujui, jalankan `npx tsx scripts/expire-reservations.ts` setiap menit dan `npx tsx scripts/sync-payments.ts` setiap menit melalui scheduler terpantau. Sinkronisasi meliputi PAID untuk mendeteksi refund yang webhook-nya hilang. Jalankan dari release yang sama dengan aplikasi dan konfigurasi gateway yang sama. Jangan menjalankan worker terhadap database asli saat proses audit ini.
- Kebijakan yang disetujui pemilik pada 25 Oktober 2026: reservasi COD berakhir H-1 pukul 18.00 WIB sesuai `requestedDate`, tetapi selalu mendapat minimal 24 jam sejak dibuat. Setelah lewat batas ini dan masih PENDING, worker boleh membatalkan serta mengembalikan stok tepat sekali. Midtrans baru tetap 24 jam sebelum checkout dimulai.
- Checkout Midtrans yang gagal tanpa token masuk `AMBIGUOUS`; penolakan validasi HTTP 400 terstruktur masuk `DEFINITIVE_FAILURE`. Keduanya menahan stok dan tampil di antrean review. Worker mengeskalasi klaim `CREATING` lebih dari dua menit, tetapi **tidak melepas stok**. Resolusi admin wajib melakukan permintaan API Midtrans authoritative yang baru, menerima terminal `expire/cancel/deny/failure`, lalu admin terautentikasi menekan tindakan resolusi. Satu 404, timeout, umur order, atau respons browser tidak cukup. Lihat `docs/PAYMENT-FULFILLMENT-STATES.md`.
- Backup/restore nyata belum dibuktikan oleh automated test. Test backfill menguji rollback transaksi pada database sintetis, bukan keberhasilan pemulihan backup pelanggan.

## Operasi harian dan pemulihan

- Monitor webhook Midtrans dan status pending, pembayaran terlambat, pesanan PAID/REVIEW, kedaluwarsa reservasi, stok negatif, batch overdue, push gagal, dan backlog waitlist. Rekonsiliasi pembayaran hanya dengan API/dashboard resmi Midtrans, bukan callback browser; jangan jalankan ulang checkout ambigu dengan order number baru. Worker expiry/reconciliation dan alokasi waitlist harus satu pemilik/lease, interval serta alarm ditetapkan operator; skrip `scripts/allocate-waitlist.ts` dapat mengubah DB: **jangan jalankan tanpa audit/backup**. Jika worker down, hentikan komitmen stok baru, cek payment & reservation manual sebelum restart. Catat waktu terakhir berhasil dan pulihkan backlog bertahap sambil pantau duplicate/double allocation.
- Akses nomor telepon, alamat, koordinat, token tautan pesanan, dan endpoint push sebagai PII/credential. Batasi hak akses dan log, enkripsi backup, gunakan TTL yang disetujui kebijakan bisnis/hukum untuk order serta backup (jangan hapus data transaksi wajib retensi), tinjau jadwal penghapusan order berakhir dan push endpoint tidak aktif; jangan menyimpan token di analytics/referrer. Saat insiden bocor token/credential: tutup akses, rotasi credential/session, batalkan tautan terdampak bila tersedia dan verifikasi transaksi eksternal.
- Ganti login admin via stdin JSON `{"username":"admin.baru","password":"frasa panjang"}` ke `npm run admin:set-login` pada DB dengan tepat satu admin. Username wajib **sudah lowercase ASCII** `a-z`, `0-9`, `.`, `_`, `-`, 3–40 karakter tanpa spasi; kata sandi minimal 12 karakter. Jangan masukkan password ke argumen CLI/history atau log; amankan stdin dan terminal. Verifikasi login baru, logout sesi lama (rotasi session secret bila perlu), simpan credential hanya di vault.
